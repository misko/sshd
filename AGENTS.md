# Instructions for independent minimal SSH server implementations

This document describes externally observable promises in English. It does not prescribe source code, programming language, libraries, process architecture, configuration syntax, or cryptographic implementation. An independent implementation may satisfy the promises in a different way.

Implement the described behavior from its externally observable requirements. Keep the minimal feature set: public-key authentication, remote commands, interactive terminals, and operator-managed identity, authorization and banner files. Do not add password login, file-transfer subsystems, forwarding, certificate authentication, or multi-factor login merely because a larger SSH product supports them. Refuse excluded capabilities safely. Do not remove assertions, automatically skip required algorithms, or reinterpret rejected security restrictions as unrestricted access to obtain a passing result. Use SSH protocol specifications for wire-level details and retain independent tests as evidence; implementation diversity alone is not evidence of security.

This is an implementation-independent acceptance contract for a minimal server. The named network scenarios, native resource-policy scenarios and cryptographic vectors below are separate acceptance groups. They establish only the stated observations; they do not prove correctness for every input or certify cryptographic security. The final section gives additional assurance obligations that every new implementation must validate for itself. No existing implementation, source tree or private interface is required to interpret these instructions.

## Environment and operator surfaces

The initial profile assumes a local Unix account, a POSIX command environment, and a writable private test directory shared with the test operator. The operator supplies the network listening address, port, server identity key, authorized public keys, login account, optional text banner file, and authentication grace period. The operator can start and stop a disposable server without changing another running service. No particular flag names or configuration grammar are required.

Each test uses a private server identity. Ordinary clients must explicitly pin that identity. An isolated interoperability client that cannot select a private trust database may be tested only against its disposable local listener, with independently pinned checks before and after; that exception does not establish the interoperability client's host-trust policy. The account has an authorized Ed25519 identity and a distinct unauthorized identity. Authentication uses public keys. The test profile neither depends on passwords nor grants arbitrary client environment variables. Unless a scenario explicitly retains a connection, use a fresh connection with one session. Interactive-shell and authentication-transition scenarios retain their connection as described. Test listeners accept connections only on the local machine.

For this profile, the required algorithm combinations are an Ed25519 server identity, Ed25519 user authentication, RSA user signatures with SHA-256 or SHA-512, ChaCha20-Poly1305 using its SSH algorithm name chacha20-poly1305@openssh.com, and each of the key exchanges curve25519-sha256 and mlkem768x25519-sha256. Compression is disabled. These are externally negotiated protocol identifiers. A future profile may declare a different set explicitly; an implementation must not silently omit a failing required combination.

## Network and authentication promises

**SSH-IDENTIFICATION.** On accepting a connection, the server announces SSH protocol version 2.0. Its identification line ends with carriage return and line feed and is at most 255 bytes including the terminator. The test does not require a particular product name or version string.

**SSH-VERSION-REJECTION.** A peer announcing SSH protocol version 1.5 is disconnected within seven seconds in this test environment. It receives less than 64 KiB of output. The listener remains available and a subsequent authorized command succeeds. This scenario does not exhaust malformed identification inputs.

**SSH-CONNECT.** A client that trusts the server identity and proves possession of an authorized private key can execute a command and receive its exact output. The command completes successfully.

**SSH-TCP-PROXY.** The same behavior works through a transparent TCP relay. Relaying the bytes without changing them does not change the authentication or command result.

**SSH-AUTH-REJECTION.** A client using the distinct unauthorized key cannot execute a requested command. A deliberately requested marker file does not appear. A subsequent authorized client can still execute a command. This scenario tests an unauthorized key; it does not cover every way that authentication might be bypassed.

**SSH-AUTH-DEADLINE.** With the authentication grace period configured to two seconds, a peer that sends no identification, and a peer that sends a valid identification then stalls, are each disconnected. The acceptance window is one to seven seconds after connection initiation, allowing up to four seconds of intentional timing variation and one second of scheduling tolerance. Each attempt produces less than 64 KiB of output. Traffic received during the wait must not extend the observation deadline. After each disconnection, an authorized command succeeds. This profile does not promise an exact two-second cutoff or establish capacity recovery at saturation.

**SSH-INTEGRITY-SERVER.** Altering the first encrypted client-to-server packet must prevent authentication and command execution on that connection. The test first establishes that the operation succeeds through an unmodified relay. For each declared key exchange, it then independently changes each of the first ten bytes of the encrypted body after the initial key transition, observes connection failure, verifies that the requested marker file was not created, and finally verifies a fresh authorized connection. Each alteration must actually occur for the test to count. A relay timeout is a test failure, not evidence of server rejection. This scenario covers the declared ChaCha20-Poly1305 cipher; it does not establish general cryptographic correctness or resistance to replay, truncation, or timing attacks.

**SSH-INTEGRITY-CLIENT-CONTROL.** Repeat the corruption matrix in the server-to-client direction. The independent client must reject the corrupted connection, and the requested command must not run. This is a control of the client and test environment rather than a claim that client behavior is implemented by the server.

## Commands and data promises

**SSH-EXIT-STATUS.** A completed command's exit status is conveyed to the client. The acceptance examples are zero, one, four, five, and forty-four. These examples must also work when the command redirects both output streams away from the connection, waits briefly, and then exits. Closing output must not manufacture a successful command result before the command finishes.

**SSH-TRANSFER.** Arbitrary bytes are preserved in both directions. The acceptance payload is 512 KiB containing repeated occurrences of every byte value. Downloading that payload, uploading it into a file, and echoing it through a command must each preserve its exact length and contents and complete successfully. Binary data must not undergo terminal text conversion when no terminal is requested.

**SSH-STDERR.** Command standard output and standard error remain distinct. When a command redirects standard output away from the connection, waits briefly, and sends 32 KiB of binary data on standard error, the complete data arrives on standard error. This must work both with no earlier standard output and with a single earlier standard-output byte, with the client using ordinary input or explicitly disconnecting its input. Completion reports success without losing the late error-stream data.

**SSH-SLOW-READER.** A client that briefly pauses reading can later receive a command's complete output without corruption or deadlock. The acceptance scenario pauses for three tenths of a second and receives exactly one hundred thousand identical lines, totaling about 1.1 MB, within fifteen seconds of resuming collection. This establishes behavior for a bounded example, not an unlimited buffering or memory guarantee.

## Terminal, banner, environment, and key transitions

**SSH-PTY.** An authorized client may request a terminal for a command. The remote command observes terminal input and output and the requested initial dimensions of twenty-seven rows and ninety-one columns. It can complete successfully. Interactive shell behavior, subsequent resize events, interrupt delivery and end-of-input behavior are checked separately below.

**SSH-BANNER.** When the operator provides a banner text file, its contents are presented to the client without becoming command standard output. The acceptance examples are empty text and printable ASCII text with a final newline, of lengths ten, one hundred, one thousand, and ten thousand bytes. The client receives exactly the configured text and can complete an authorized command. These examples do not establish the handling of arbitrary Unicode, missing files, oversized files, live edits, or the exact point during authentication when the banner is delivered.

**SSH-ENV-DENIAL.** A client cannot inject an arbitrary environment variable into the command environment. An unapproved variable sent during session setup remains absent when inspected by the remote command. This profile does not require an environment-variable allowlist feature.

**SSH-KEX-CIPHER.** Each declared key exchange can be negotiated with the declared cipher and can support an authenticated command with exact output. The client observes the expected negotiated choices. There is no implicit requirement to support every algorithm offered by a particular client.

**SSH-REKEY.** A client may request fresh encryption keys during an active connection. For each declared key exchange and client data thresholds of sixteen bytes, one KiB, sixty-four KiB, one hundred twenty-eight KiB and two hundred fifty-six KiB, a one MiB binary echo completes without corruption or command failure. The client observes at least one completed key transition beyond the initial exchange in both directions. This scenario does not establish simultaneous-transition behavior; server-originated renewal and client timers have separate scenarios below.

## Additional identity and policy acceptance scenarios

**SSH-HOST-KEY-SCAN.** Three successive unauthenticated key scans must return exactly the configured Ed25519 server identity. A subsequent authorized command must succeed. A scan does not independently establish that a previously unknown identity is trustworthy.

**SSH-RSA-SHA2.** Authorized RSA user keys of 2,048 and 3,072 bits must each authenticate using SHA-256 and SHA-512 signatures. For each of the four combinations, the independent client observes the chosen signature algorithm and receives exact output from an authorized command. This requirement does not enable RSA host identities or RSA signatures using SHA-1.

**SSH-ACCOUNT-DENIAL.** Possession of a valid authorized private key does not grant access to another account. The same key must fail for a nonexistent account and for an existing account other than the configured one. A requested marker file must not be created, and a subsequent authorized login to the configured account must succeed.

**SSH-METHOD-DENIAL.** The server advertises only public-key authentication. Clients limited to no authentication, passwords, keyboard-interactive authentication, or host-based authentication fail to execute a requested command. These scenarios observe method advertisement and the absence of successful login; they do not inject every malformed request for those methods.

**SSH-AUTHORIZED-KEY-LINES.** An authorization file may contain blank lines, comments, multiple public keys and trailing descriptive comments. Each valid listed identity can authenticate independently. Descriptive comments do not change which key is authorized.

**SSH-IDENTITY-FALLBACK.** After a client offers an unauthorized key, it may offer an authorized key on the same connection and successfully execute a command, within the authentication attempt limit. The test must observe both offers. This is different from requiring two keys for one login.

**SSH-KEY-FORCED-COMMAND.** A key restricted to a forced command must never execute the client's replacement command. The implementation may enforce the restriction and return the forced command's result, reject that restricted key, or reject the unsupported configuration before listening. Test both a forced command alone and a forced command combined with a terminal prohibition. Successful unrestricted login is established first as a control.

**SSH-KEY-PTY-RESTRICTION.** A key that forbids terminals, including a general restricted key whose policy includes a terminal prohibition, must not obtain a terminal. Refusing the restricted key or rejecting unsupported configuration before listening is also acceptable. A normal unrestricted key must first be shown to obtain a terminal.

**SSH-KEY-SOURCE-EXPIRY.** A key restricted to a source address or network that excludes the client must not authenticate. An expired key, a key with an invalid expiry restriction, and a key with an unknown restriction must not authenticate. Explicit rejection of unsupported configuration before listening is acceptable. Unknown restrictions must never silently become unrestricted authorization.

**SSH-BROKEN-AUTHORIZED-KEY.** Empty or malformed authorization input must not grant access. The acceptance cases include truncated RSA material and invalid Ed25519 encoding. If a file contains both a malformed entry and a valid entry, the implementation may reject the whole configuration, or ignore the malformed entry and honor the valid one. A malformed entry must never itself authorize a key. Configuration rejection must be a normal error termination, not a process crash.

**SSH-AUTHORIZED-KEY-PERMISSIONS.** An authorization file writable by unrelated users must not enable login. The server may reject the configuration before listening or refuse authentication from that file. A safe-permission file with identical authorization material must work as a control.

**SSH-HOST-KEY-FAIL-CLOSED.** A missing, truncated, or publicly writable private server identity must prevent listener startup. The server must terminate with a normal configuration error rather than crash, generate an unnoticed substitute identity, or accept unprotected sessions. A valid private identity must work as a control.

## Reload and excluded capabilities

**SSH-RELOAD.** After the operator requests a reload of unchanged valid configuration, new authorized commands must succeed within five seconds, both with and without an existing unauthenticated stalled connection. The tested identity remains pinned. This requirement does not prescribe a signal, configuration format, process replacement mechanism, or the fate of existing authenticated sessions.

**SSH-KEY-REVOCATION.** Replacing the authorization file and requesting reload must enable the newly authorized key within five seconds. The removed key must then fail to execute a new command. The configured server identity must remain trusted throughout this transition. This scenario concerns new sessions after reload, not retroactive revocation of an already running command.

**SSH-BANNER-RELOAD.** Replacing the configured banner text and requesting reload must make the new text visible on a new successful connection within five seconds. Both the old and new text must be observed at the appropriate stages. No change of server identity is permitted.

**SSH-BANNER-UNAUTHORIZED.** A client whose key is rejected must still receive the configured authentication notice exactly, without successfully executing a command.

**SSH-FORWARD-LOCAL-DENIAL.** A request for a direct TCP forwarding channel must be refused. The test must observe a channel rejection and verify that a separately listening destination receives no connection. A subsequent ordinary authorized command must succeed.

**SSH-FORWARD-REMOTE-DENIAL.** A request to create a remotely forwarded TCP listener must be refused. The client must observe a forwarding failure, and a subsequent ordinary command must succeed.

**SSH-SUBSYSTEM-DENIAL.** Requests for SFTP and an unknown subsystem must be refused explicitly, while ordinary authorized commands continue to work. This requirement does not grant access to file operations through a subsystem. An unrestricted command account can still invoke programs available to that operating-system account.

**SSH-CERTIFICATE-DENIAL.** A certificate signed by an untrusted authority must not authenticate, even when its underlying bare public key is otherwise authorized. The test must observe an actual certificate offer and prevent fallback to the bare key during the negative attempt. A subsequent bare-key login must still work.

## Additional command, terminal and transport scenarios

**SSH-INTERACTIVE-SHELL.** An authorized client can start a shell with a terminal, send a command, and receive its expected output. Sending terminal end-of-input must terminate the shell and report success within five seconds.

**SSH-TERMINAL-INTERRUPT.** A terminal interrupt must stop a foreground command that would otherwise wait eight seconds. Within three seconds, the same shell must accept and execute a subsequent command. The interrupted command must not reach its final output, and the shell must remain usable and be able to exit successfully.

**SSH-TERMINAL-RESIZE.** After terminal allocation, changing the client's dimensions must become visible to a remote terminal query within three seconds. Exercise two successive changes, to thirty-seven rows by one hundred thirteen columns and then eighteen rows by seventy columns. The shell must remain usable.

**SSH-COMPRESSION-FALLBACK.** With compression disabled by the server profile, both a client requesting compression and a client disabling it must complete an exact-output command. Both directions negotiate no compression.

**SSH-ALGORITHM-DENIAL.** A client restricted to a key exchange or cipher outside this profile must not connect. The acceptance examples are finite-field group-exchange SHA-256 and AES-128 in counter mode. The client must observe a negotiation mismatch rather than a local option-parsing failure, and a subsequent supported connection must succeed.

**SSH-TRANSFER-BLOCKS.** Upload the same 512 KiB binary payload using client writes of ten, one hundred, 1,024, 32,768, 65,536, 131,072 and 262,144 bytes. Every resulting file must exactly match the payload and complete within fifteen seconds. These write boundaries are not claims about TCP packet boundaries.

**SSH-REKEY-TIMER.** A client's one-second key-renewal timer must be honored while a command remains active. The test uses a data threshold too large to trigger renewal, observes another complete key transition in both directions, and receives the command's exact output. This covers a client timer, not a server-originated timer.

**SSH-AUTH-INFO-DENIAL.** With authentication-detail export disabled, a client must not inject a variable that purports to identify an authentication-information file. The remote command must observe that variable as absent.

**SSH-SESSION-LIMIT.** Once an authenticated connection owns a session channel, a second simultaneous session channel must be rejected. The original channel must remain usable and complete an authorized command with exact output and status. A separate fresh authenticated connection must still work.

**SSH-FORWARD-PROTOCOL-DENIAL.** Explicit protocol requests for direct TCP, direct Unix-domain, remote TCP and remote Unix-domain forwarding must all be refused. Listening test destinations must receive no connection, and the remote Unix-domain listener path must not be created. The original session must still execute a normal command. SOCKS and jump-host clients cannot bypass this policy by requesting the same underlying direct-forwarding channel.

**SSH-REQUEST-DENIAL.** Explicit requests for X11 forwarding, authentication-agent forwarding, a file-transfer subsystem and injection of a dynamic-loader environment variable must receive failure replies. An unknown global request asking for a reply must be rejected. The connection must remain usable for a normal command. Flow-control messages that occur between a request and its reply are permitted and must not be mistaken for success or failure of that request.

**SSH-AUTH-REQUEST-DENIAL.** A protocol peer that actually sends no-authentication and password-authentication requests must receive authentication failures. It may subsequently authenticate with the authorized public key and execute a normal command. This checks explicit requests in addition to the method-advertisement scenarios.

**SSH-DUPLICATE-EXEC.** After a command has been accepted on a session channel, a second execution request on that channel must receive failure. The first command must still complete with its own exact output and exit status, without the replacement command's output.

**SSH-DISCONNECT-CLEANUP.** When a client disconnects from a terminal session whose shell has become a running foreground process, that process must terminate and be reaped within three seconds. A terminated but unreaped process is not sufficient. A new authorized connection must succeed afterward. This scenario observes the process identifier supplied by the test command rather than relying on the daemon's internal process model.

## Further independent-peer and authentication scenarios

**SSH-PUTTY-INTEROP.** An independent PuTTY client must complete binary upload, download and duplex echo using each declared key exchange and ChaCha20-Poly1305 in both directions. Repeat with compression requested and disabled; the server still negotiates no compression. Upload using each of the seven write sizes described earlier. Verify exact bytes, successful completion and the client's observed algorithm choices. Pin the fixture server identity.

**SSH-DROPBEAR-INTEROP.** An independent Dropbear client must complete exact binary upload, download and duplex echo with the declared cipher and a mutually supported key exchange. An optimistic initial key-exchange packet must not break compatibility. This scenario does not require that client to select each exchange independently or establish host-trust behavior where its fixture isolation requires the trust-database exception above.

**SSH-STRICT-KEX-GUESS.** When strict key exchange is negotiated and the client declares an optimistic guess that does not match negotiation, exactly that one guessed packet may be ignored. A subsequent valid exchange must produce the server's exchange response and transition to new keys. An unexpected ignore message after the discarded guess, a second malformed guess, an undeclared ignore message after negotiation, or a premature transition to new keys must cause a protocol disconnect or connection closure within two seconds. The authentication deadline is five seconds, so merely waiting for that deadline cannot pass the rejection checks. A fresh authorized connection must still work. This requirement concerns observable protocol order and does not prescribe counters or state representation.

**SSH-REKEY-SERVER.** The server must initiate and complete key renewal during a download of one GiB plus one MiB. Every byte must arrive correctly and the command must report success within fifty-five seconds on the declared local test host. The observing client's automatic byte threshold must exceed the transfer and its renewal timer must exceed the observation period; no explicit client renewal request is made. The peer must observe at least two completed exchanges including the initial one. A client that silently enforces a lower cipher-specific threshold cannot prove server initiation merely by setting a larger requested threshold. This scenario covers a server data threshold, not an hour-long server timer or a throughput promise on arbitrary hardware.

**SSH-SIGNATURE-BINDING.** Offering an authorized public key is insufficient to authenticate. Reject an altered signature, a signature over a different session identifier, a signature over a different username, and a signature produced by a different private key. Each negative test must actually transmit the signature. On the same connection, a correctly signed request produced by the same test peer must subsequently authenticate and execute an exact-output command. This positive control prevents malformed test framing from masquerading as cryptographic rejection.

## Cumulative preauthentication and source-policy promises

**SSH-PREAUTH-BYTE-BUDGET.** Every unauthenticated connection has a cumulative receive allowance of 262,144 SSH wire bytes and a separate cumulative send allowance of 262,144 SSH wire bytes. Include the identification exchange, packet headers, padding, ciphertext and authentication tags. These allowances cover the entire unauthenticated lifetime; packet boundaries, key changes, offered keys and failed authentication attempts do not reset them. Do not wait for another byte or the authentication timer after a receive allowance has been consumed. Terminate the affected connection when an allowance is exhausted. Remove the allowances only after successful authentication, never after an unsigned key offer or a provisional authorization response. Bytes merely queued in bounded operating-system socket buffers and TCP/IP overhead are outside this application-byte accounting.

Acceptance must include a below-limit control, a stream of many small valid transport packets, and a fragmented stream of individually permitted large packets. Both attack streams must be closed before a thirty-second authentication deadline, within a three-second observation period for the bounded local test. A new authorized login must work after each rejection. Separately establish exact-boundary accounting, partial writes and reads, temporary inability to make progress, concurrent access to the same connection, and larger authenticated transfers. Send accounting must cover both ordinary and multi-buffer writes. Prove the cumulative limit independently of the single-packet limit; rejecting one oversized packet is insufficient.

**SSH-PENALTY-EXPIRY.** Track failed admitted connections by source IP address. Five failed connections during the preceding thirty minutes activate a thirty-minute ban. Count a connection once, regardless of how many keys it offers. A connection that successfully authenticates does not count as a failure, but success does not erase failures from previous connections. Abandoning a connection before authentication counts as a failure. Ordinary administrative shutdown must not manufacture attack failures. Reject banned sources before expensive authentication work. A rejected retry must not extend an existing ban. Reload must preserve active history and bans; a full service restart may clear this deliberately in-memory state. Treat IPv4 and its IPv4-mapped IPv6 representation as the same source. Any loopback exemption must be explicit and off by default.

The timed acceptance scenario must use real elapsed time. Four failures, each followed by a successful login, remain below threshold; the fifth activates the ban. Verify continued denial after one second, one minute, five minutes, fifteen minutes and just before expiry. Include a reload and healthy access from another source. Just after thirty minutes, a correct key must authenticate again despite the earlier denied retries. On another source, one failure older than thirty minutes must not contribute to a new group of four; a fresh fifth failure must still ban. Shortened production timers or a mocked clock cannot substitute for this end-to-end expiry observation.

**SSH-PENALTY-CAPACITY.** Keep failure history and active bans in memory with independent finite capacities. The default capacity is ten thousand source addresses in each table. Auxiliary expiry or ordering information must remain bounded too; discarded and expired entries must not leave an ever-growing secondary history. The operator may choose smaller capacities. Before retaining a new source when a table is full, discard the oldest failure history or the active ban with the earliest expiry, respectively. Do not transiently exceed the configured entry count. This policy deliberately permits an evicted source to try again; a finite blacklist cannot remember every attacker forever.

Acceptance must expose eviction through subsequent login behavior with three failure-history entries and two ban entries. A discarded history must no longer contribute to the fifth-failure threshold, while a retained history still does. Adding a third ban must release the earliest-expiring one and preserve the other two. Churning the history table must not erase independent active bans or kill the listener. Five abandoned connections must also trigger a ban. Separately verify both actual default ten-thousand-entry bounds under churn; small-capacity behavior alone does not prove allocation or memory bounds at the default size.

## Cryptographic acceptance independent of implementation

**CRYPTO-ED25519-VECTORS.** For all three published Ed25519 vectors in the pinned OpenSSH cryptographic regression source, derive the exact expected public key from the supplied seed, produce the exact expected deterministic signature for the supplied message, and verify the supplied valid signature. Reject a signature with an altered byte. These are input/output requirements; no particular arithmetic, object layout or cryptographic library is required.

**CRYPTO-MLKEM-VECTORS.** For all five published ML-KEM-768 vectors in that source, given the vector's public encapsulation key and encapsulation randomness, produce a ciphertext of 1,088 bytes with the specified SHA3-256 hash and the exact specified shared secret. The public key must be 1,184 bytes and match the vector's public-key hash. If the upstream fixture supplies only the key-generation seed, an independent fixture generator may expand it, but its public key must match that published hash before use. This server-side profile requires encapsulation; it does not require the server to implement client-side ML-KEM private-key generation or decapsulation. Passing known answers is necessary evidence, not a substitute for negative-vector, entropy-failure or side-channel evaluation.

## Operator, lifecycle and resource assurance obligations

These obligations supplement the ported interoperability scenarios. A new implementation must produce its own evidence for them; passing the named network scenarios alone does not establish them.

The operator interface must document the listening address and port, the served account and its actual operating-system privileges, the command working directory, the host identity and authorized-key files, the optional banner file, authentication and command deadlines, admission capacity, source admission policy, and table capacities. Reject invalid settings before accepting clients. A requested root account provides root command privileges and must be an explicit operator choice. A client-supplied username must never select additional operating-system privileges. Define the permitted environment and executable-command semantics; arbitrary command access inherently includes the account's ordinary file and program capabilities.

The host identity must remain stable across ordinary key-list or banner reloads. Missing or unsafe identity material must not silently generate a replacement. Authorization changes must take effect on new connections within the reload deadline. State explicitly whether existing authenticated sessions survive or are terminated by reload; neither behavior may silently retain revoked authorization for new sessions. Invalid replacement authorization must fail closed. Administrative stop must cease new admissions, terminate owned command sessions and release their resources within a documented deadline. A deployment supervisor may restart a crashed service, but restart does not satisfy a promise that hostile traffic cannot crash it.

Banner input must be a regular text file, contain valid UTF-8 without NUL, and contain at most sixteen KiB. Empty input means no notice. Missing, unreadable, oversized or invalid configured banner input must cause a clear configuration failure. Reading a special file must not block startup or reload indefinitely. Banner output must remain separate from command output. Test the exact size boundary, Unicode, invalid bytes, NUL, missing files, special files and replacement during reload.

Declare a finite maximum for admitted connections, per-source admission and queued expensive work. Connection and authentication deadlines begin from the original acceptance event and are not renewed by dripping data or repeated key exchange. No unauthenticated peer may run a command, allocate an unlimited collection of channels, enlarge an unbounded queue or force unbounded work from one claimed length. Incoming transport packets must be limited to 35,000 bytes while preserving the profile's supported legal packets. Validate lengths and protocol order before allowing a claimed size to drive large resource consumption. Cumulative byte limits, packet limits, deadlines, work limits and connection limits are separate protections and must be tested separately.

For every claimed capacity, record the operating system, CPU and memory allocation, descriptor limits, configured admission limits, client workload, peak memory, observation duration and recovery deadline. Release simultaneous connection attempts together; a delayed sequence is not evidence of simultaneous capacity. Test at and above the configured admission capacity and near the descriptor limit. Under ordinary descriptor exhaustion or temporary network-buffer pressure, the service must remain alive and may temporarily reject or defer new connections. Existing authenticated work must remain usable within the declared resource envelope. After clients release resources, new authorized access must recover. These promises do not imply survival after the operating system forcibly terminates the process or under an unspecified, unlimited host-wide resource attack.

Cover malformed and truncated framing, message sequencing, replays, channel flow control, EOF and close ordering, duplicate requests, subprocess descendants and cancellation. Preserve the authentication binding to the exact session, account, service, method and public key. Use secure randomness where the protocol requires it and fail closed if randomness is unavailable. Do not substitute a new cryptographic protocol merely to obtain implementation diversity. Validate each algorithm independently, assess timing and secret-lifetime risks, and document dependency and operating-system trust assumptions.

Diagnostic output must omit private keys, authentication secrets and session plaintext. Bound queued and emitted diagnostics under repeated failures; a blocked logging destination must not indefinitely stall acceptance, shutdown or authentication. Tests must include rejection and recovery rather than only successful login. Record test inputs, expected observations, deadlines, exact tested artifact identity and every intentional profile exclusion. Never silently skip a required behavior, remove a failing assertion, or equate a passing implementation with a complete security proof.

## Source scope and use by new agents

The source review is pinned to [OpenSSH portable revision 97648317199613d06247bf4cc4d44a95f250c532](https://github.com/openssh/openssh-portable/tree/97648317199613d06247bf4cc4d44a95f250c532/regress). It accounts for all 116 top-level shell scripts, the ten file-test targets and all 42 C unit-test source files at that revision. The portable server scenarios draw from 48 shell scripts; remaining scripts concern companion clients and tools, excluded capabilities, the harness or OpenSSH-specific implementation choices. This contract adapts their observable properties within the declared minimal profile. It does not require executing the original harness or reproducing every assertion of OpenSSH's larger feature set.

Use the [SSH transport specification](https://www.rfc-editor.org/rfc/rfc4253), [authentication specification](https://www.rfc-editor.org/rfc/rfc4252), [connection specification](https://www.rfc-editor.org/rfc/rfc4254) and the pinned [OpenSSH protocol extensions](https://github.com/openssh/openssh-portable/blob/97648317199613d06247bf4cc4d44a95f250c532/PROTOCOL) to resolve wire details. The [Ed25519 vectors](https://github.com/openssh/openssh-portable/blob/97648317199613d06247bf4cc4d44a95f250c532/regress/unittests/crypto/test_ed25519.c) and [ML-KEM vectors](https://github.com/openssh/openssh-portable/blob/97648317199613d06247bf4cc4d44a95f250c532/regress/unittests/crypto/test_mlkem.c) supply published expected values and carry their own public-domain notices. Preserve each source's applicable attribution when porting material; OpenSSH as a whole does not have one uniform license.

Implement from these English requirements with your chosen design, then construct independent stimuli and observations for every acceptance group. Keep configuration adapters separate from behavioral expectations. Exercise the result with independent clients, including negative and recovery scenarios. Maintain a traceable requirement-to-test record and an explicit list of unverified obligations. Any revision that changes a promise must explain the externally observable change, not prescribe how the code achieves it.
